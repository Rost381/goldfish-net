# Сетки ордеров на Binance USDT-M Futures

Проект из двух скриптов для выставления сеток ордеров из одного и того же CSV с уровнями. Общее для обоих: подключение через ccxt, ключи из `.env`, режимы `real` / `demo` / `testnet`, формат аргументов `SYMBOL SIDE FILE [EXCHANGE] [MODE]`, проверки перед отправкой, **проверка по бирже, что ордера реально стоят**, запись итогового файла.

| Файл | Назначение |
|---|---|
| `place_limit_grid.py` | Сетка **лимитных** ордеров: short = SELL выше рынка, long = BUY ниже рынка. Ордера уходят batch-запросами. [Часть 1](#часть-1-place_limit_gridpy--сетка-лимитных-ордеров-на-binance-usdt-m-futures) |
| `place_market_grid.py` | Сетка **условных рыночных** ордеров (`STOP_MARKET` / `TAKE_PROFIT_MARKET`) в любом месте относительно цены, с опциональными Take-Profit (`-p`) и Stop-Loss в безубыток (`-b`). Только hedge-режим. [Часть 2](#часть-2-place_market_gridpy--сетка-условных-рыночных-ордеров) |
| `cancel_grid.py` | Удаляет ордера сетки по файлу, записанному `place_limit_grid.py` или `place_market_grid.py`; проверяет наличие ордеров перед удалением, использует batch-отмену, не трогает TP/SL уже сработавших входов. [Часть 3](#часть-3-cancel_gridpy--удаление-ордеров-сетки) |
| `probe_close_orders.py` | Разовая проба на demo/testnet: какие условные ордера принимает биржа без открытой позиции. Нужна была для проектирования TP/SL, [см. раздел 2.12](#212-проба-probe_close_orderspy) |
| `.env.example`, `requirements.txt` | Шаблон ключей и зависимости |
| `README_LLM.md` | Описание проекта на английском для нейросети (продолжение работы в новом чате); человеку не нужен |

`place_market_grid.py`, `cancel_grid.py` и `probe_close_orders.py` импортируют общие функции из `place_limit_grid.py`, поэтому **все файлы должны лежать в одной папке**.

# Часть 1. place_limit_grid.py — сетка лимитных ордеров на Binance USDT-M Futures

Скрипт читает CSV с ценовыми уровнями и размерами, проверяет данные и выставляет сетку **лимитных ордеров** через batch-запросы. После выставления он **сверяется с биржей**, что все ордера действительно стоят, добивает недостающие по одному и сохраняет итог в файл.

Направление задаётся обязательным аргументом `SIDE`:

| SIDE | Что выставляется | Где должны быть уровни |
|---|---|---|
| `short` | лимитные **SELL** | **выше** текущей цены |
| `long` | лимитные **BUY** | **ниже** текущей цены |

Take-profit и stop-loss **не ставятся**. Тип ордеров: `LIMIT`, `GTC`. Логика `long` — точное зеркало `short`.

## 1. Требования и установка

- Python **3.12 или новее**
- Библиотеки: `ccxt` (последняя версия; проверено на 4.5.91), `python-dotenv`

Windows (PowerShell):

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Linux / macOS:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

## 2. Настройка ключей (.env)

Скопируйте `.env.example` в `.env` (рядом со скриптом) и заполните ключи **для тех режимов, которыми пользуетесь**:

```env
BINANCE_API_KEY=...              # real
BINANCE_API_SECRET=...

BINANCE_DEMO_API_KEY=...         # demo
BINANCE_DEMO_API_SECRET=...

BINANCE_TESTNET_API_KEY=...      # testnet
BINANCE_TESTNET_API_SECRET=...
```

У каждого режима **свои ключи**, ключи от одного режима в другом не работают. Если нужных переменных нет, скрипт сразу сообщит, какие именно добавить.

Права API-ключа: достаточно чтения и торговли фьючерсами (Enable Futures). Вывод средств включать не нужно.

> Файл `.env` не должен попадать в git.

## 3. Формат входного CSV

Пример:

```csv
Level;Size;
2.51998400;14.00;
2.59558352;16.00;
2.67345103;20.00;
```

- **Level** — цена уровня.
- **Size** — размер ордера в **USDT целиком** (полная стоимость позиции ордера), а не начальная маржа. Количество монет считается как `Size / цена`, поэтому плечо на количество не влияет.
- Первая непустая строка — заголовок с колонками `Level` и `Size` (регистр не важен, порядок колонок любой).
- **Разделитель полей** определяется автоматически по заголовку: `;`, `,`, пробел, табуляция, `|` и т. п.
- **Десятичный разделитель** — точка или запятая: `2.5` и `2,5` читаются одинаково.
- Пустые строки и строки вида `;;` пропускаются. Кодировка UTF-8 (с BOM или без) или cp1251.
- Максимум **50 уровней**.

Скрипт остановится с понятным сообщением, если: нет заголовка, число нечитаемо, заполнено только одно поле строки, колонок больше, чем в заголовке (типичный случай: запятая и как разделитель полей, и как десятичная), число неоднозначно (`1,234.5`), уровней больше 50.

## 4. Запуск

### Позиционные аргументы

```
python place_limit_grid.py SYMBOL SIDE FILE [EXCHANGE] [MODE]
```

| Аргумент | Обязателен | По умолчанию | Описание |
|---|---|---|---|
| `SYMBOL` | да | — | Фьючерсный символ, например `BTCUSDT`. Регистр не важен, приводится к верхнему. Должен оканчиваться на `USDT` |
| `SIDE` | да | **нет** | `long` или `short`, регистр не важен (`Long`, `SHORT`, `loNg`) |
| `FILE` | да | — | Путь к CSV |
| `EXCHANGE` | нет | `binance` | Пока поддерживается только Binance |
| `MODE` | нет | `demo` | `real`, `demo` или `testnet` |

Допустимо (биржу можно опустить):

```powershell
python place_limit_grid.py ESPORTSUSDT short Bot_levels.csv
python place_limit_grid.py ESPORTSUSDT Long Bot_levels.csv real
python place_limit_grid.py ESPORTSUSDT SHORT Bot_levels.csv binance real
```

**Недопустимо** — порядок аргументов должен быть именно такой:

```powershell
python place_limit_grid.py ESPORTSUSDT Bot_levels.csv           # нет SIDE
python place_limit_grid.py ESPORTSUSDT Bot_levels.csv short     # SIDE не на втором месте
python place_limit_grid.py ESPORTSUSDT short real Bot_levels.csv binance   # режим вместо файла
python place_limit_grid.py ESPORTSUSDT short Bot_levels.csv real binance   # режим перед биржей
```

### Ключи (по желанию)

Ключи не обязательны, но работают и дают тот же результат:

```powershell
python place_limit_grid.py --symbol ESPORTSUSDT --side short --file Bot_levels.csv --exchange binance --mode real
```

Сокращения: `-s` (symbol), `-f`, `-e`, `-m`; у `--side` сокращения нет. Можно смешивать: `python place_limit_grid.py ESPORTSUSDT short Bot_levels.csv --mode real`. Если одно и то же задано и позиционно, и ключом, будет ошибка.

### Дополнительные флаги

| Флаг | Назначение |
|---|---|
| `--dry-run` | Выполнить все проверки и показать план (уровни, количества, суммы), **не отправляя ордера**. Рекомендуется перед первым боевым запуском |
| `--allow-marketable` | Разрешить уровни, которые исполнятся сразу по рынку: для `short` — не выше текущего bid, для `long` — не ниже текущего ask. По умолчанию это ошибка |

## 5. Режимы real / demo / testnet

| Режим | Что это | Хост API | Ключи |
|---|---|---|---|
| `real` | Реальный счёт | `fapi.binance.com` | `BINANCE_API_KEY/SECRET` |
| `demo` | Demo Trading реального аккаунта Binance | `demo-fapi.binance.com` | `BINANCE_DEMO_API_KEY/SECRET` |
| `testnet` | Отдельный Futures Testnet | `testnet.binancefuture.com` | `BINANCE_TESTNET_API_KEY/SECRET` |

Это **три разных окружения**: у них разные ключи, балансы, наборы символов и ценовые данные. В demo и testnet символов заметно меньше, чем в real, поэтому символ, который есть в real, может отсутствовать в demo — скрипт проверяет это отдельно для выбранного режима.

> Режимы `real` и `demo` проверены на практике. Режим `testnet` пока не тестировался на живой бирже: в документации Binance адреса testnet сейчас описаны неоднозначно (в разных разделах указаны `demo-fapi.binance.com` и `testnet.binancefuture.com`). Скрипт использует адрес ccxt (`testnet.binancefuture.com`). Если при первом запуске появятся ошибки подключения, это первое, что нужно проверить.

## 6. Что делает скрипт по шагам

1. Разбирает аргументы, приводит символ и `SIDE` к нужному регистру, проверяет, что символ оканчивается на `USDT` (до любых обращений к бирже).
2. Читает и проверяет CSV.
3. Создаёт клиента ccxt для выбранного режима и загружает рынки.
4. Проверяет, что символ торгуется в этом режиме, и запрашивает по нему данные (текущую цену).
5. Получает **текущее плечо** символа (для `short` — плечо шорта, для `long` — плечо лонга) и **режим позиций** (one-way или hedge). В hedge-режиме ордера `short` ставятся с `positionSide=SHORT`, ордера `long` — с `positionSide=LONG`.
6. Рассчитывает ордера, округляя цену до `tickSize`, а количество вниз до `stepSize`. Выполняет все проверки (раздел 7). При любой ошибке **ничего не отправляется**.
7. Выставляет ордера batch-запросами по 5 штук.
8. Проверяет по бирже, что каждый ордер стоит; недостающие выставляет по одному и снова проверяет (раздел 8).
9. Печатает итоговую таблицу и записывает файл с установленными ордерами (раздел 9).

## 7. Проверки перед отправкой

| Проверка | Что происходит при нарушении |
|---|---|
| Структура CSV (раздел 3) | Ошибка, ордера не отправляются |
| Символ оканчивается на `USDT` | Ошибка до обращения к бирже |
| Символ торгуется в выбранном режиме, статус `TRADING`, расчёты в USDT | Ошибка; показываются похожие символы |
| По символу приходят данные (цена) | Ошибка |
| Уровень отличается от текущей цены не более чем в **10 раз** в любую сторону | Ошибка с номером строки |
| `short`: уровень не выше текущего bid. `long`: уровень не ниже текущего ask (ордер исполнился бы сразу по рынку) | Ошибка (если не указан `--allow-marketable`) |
| Цена в допустимых пределах символа | Ошибка |
| Два уровня совпали после округления до `tickSize` | Ошибка |
| Количество не меньше минимального и не больше максимального | Ошибка |
| Стоимость ордера не ниже минимальной (min notional) | Ошибка |
| На тех же ценах уже стоят ваши ордера того же направления (защита от двойного запуска) | Ошибка |
| Нужная маржа (`сумма сетки / плечо`) больше доступного баланса | Предупреждение |
| Сумма сетки выше лимита позиции для текущего плеча | Предупреждение |
| Из-за шага лота стоимость ордера заметно меньше `Size` | Предупреждение |

Все ошибки собираются и выводятся одним списком, а не по одной.

## 8. Как гарантируется, что ордера реально стоят

Особенности batch-запроса Binance (`POST /fapi/v1/batchOrders`, до 5 ордеров):

- Ордера в пачке обрабатываются независимо: часть может пройти, часть быть отклонена.
- В ответе на каждый ордер приходит либо ордер, либо ошибка с кодом.
- Запрос может завершиться таймаутом, хотя биржа ордера приняла.

Поэтому ответ batch используется только для логов, а **источником истины считается биржа**:

1. Каждому ордеру присваивается уникальный `clientOrderId` вида `sg<ГГММДДччммсс>-<номер>` для `short` и `lg<ГГММДДччммсс>-<номер>` для `long`.
2. После отправки запрашиваются открытые ордера по символу, и каждый ордер сопоставляется по `clientOrderId`, а также сверяются сторона (SELL для `short`, BUY для `long`), цена и количество.
3. Для ордеров, которых нет среди открытых, запрашивается статус по `clientOrderId`:
   - **биржа отвечает «такого ордера нет»** — ордер выставляется отдельным запросом;
   - **ордер уже исполнен, отменён или истёк** — повторно **не ставится** (иначе позиция задвоилась бы), попадает в отчёт как проблемный;
   - **статус получить не удалось** (сеть) — тоже не ставится повторно, попадает в отчёт.
4. После повторов делается новая проверка. Всего до 3 раундов повторов.

Повторная отправка с тем же `clientOrderId` безопасна: дубль не создастся.

## 9. Файл с установленными ордерами

После выставления ордера записываются в CSV. Папка зависит от режима (создаётся автоматически рядом со скриптом):

| Режим | Папка |
|---|---|
| `real` | `placed_orders/` |
| `demo` | `demo_placed_orders/` |
| `testnet` | `testnet_placed_orders/` |

Имя файла: `SYMBOL_Short_Limit_ДД.ММ-чч.мм.csv` для `short` и `SYMBOL_Long_Limit_ДД.ММ-чч.мм.csv` для `long`, по **локальному времени машины**. Например:

```
placed_orders/ESPORTSUSDT_Short_Limit_02.11-12.15.csv
demo_placed_orders/ESPORTSUSDT_Long_Limit_02.11-12.15.csv
```

Если в ту же минуту файл с таким именем уже есть, добавляется суффикс `_2`, `_3`, … (файл не перезаписывается).

Содержимое:

```csv
Level;Coins;USDT;OrderId;ClientOrderId
2.519984;5.5;13.859912;123456789;sg261102121500-01
```

- **Level** — цена ордера **как на бирже** (после округления до `tickSize`).
- **Coins** — количество монет **как на бирже** (после округления до `stepSize`).
- **USDT** — реальная стоимость ордера: `Level × Coins`. Она может немного отличаться от `Size` в исходном CSV из-за округления.
- **OrderId** и **ClientOrderId** — идентификаторы на бирже.

Значения берутся из ответа биржи, а не из расчёта скрипта. В файл попадают только ордера, которые **подтверждённо стоят** на бирже. Исполненные, отменённые и не выставленные ордера в файл не входят (они перечислены в итоговом отчёте в консоли). Если подтверждённых ордеров нет, файл не создаётся.

## 10. Коды выхода

| Код | Значение |
|---|---|
| `0` | Все ордера подтверждены на бирже (или `--dry-run` прошёл успешно) |
| `1` | Ошибка аргументов, конфигурации или проверок. **Ничего не отправлено** |
| `2` | Часть ордеров не удалось выставить или подтвердить; список проблемных указан в итоге |

## 11. Частые ошибки

| Сообщение | Причина и решение |
|---|---|
| `Для mode=demo в .env нужны ...` | Не заполнены ключи нужного режима в `.env` |
| `Биржа отклонила ключи` | Ключи от другого режима или у ключа нет прав на фьючерсы |
| `Символ ... не торгуется на binance в режиме demo` | В demo/testnet меньше символов, чем в real; проверьте режим или символ |
| `Символ ... должен оканчиваться на USDT` | Скрипт работает только с USDT-M контрактами |
| `Вторым аргументом должен быть SIDE` | Не указан или указан не на втором месте `SIDE` (`long` / `short`). Порядок: `SYMBOL SIDE FILE [EXCHANGE] [MODE]` |
| `Третьим аргументом должен быть путь к CSV` | Нарушен порядок аргументов |
| `отличается от текущей цены ... более чем в 10 раз` | Опечатка в уровне или не тот символ |
| `SELL-лимит не выше текущего bid` / `BUY-лимит не ниже текущего ask` | Уровень «не с той стороны» от рынка: ордер исполнился бы сразу. Проверьте `SIDE` и уровни или используйте `--allow-marketable` |
| `стоимость ордера ... меньше минимальной` | Увеличьте `Size` для этого уровня |
| `уже стоит ордер того же направления` | Сетка уже выставлена; отмените старые ордера, если хотите выставить заново |
| `Margin is insufficient` (код `-2019`) в логе | Не хватает маржи: уменьшите размеры или увеличьте плечо/баланс |

## 12. Ограничения и важные замечания

- Лимит **5 ордеров на batch** взят из актуальной документации Binance. Если Binance его изменит, правится константа `BATCH_SIZE` в начале скрипта (через API это значение не отдаётся).
- Скрипт **не меняет** плечо, тип маржи и режим позиций, а использует текущие настройки аккаунта по символу.
- Скрипт **не отменяет** существующие ордера.
- Поддерживается только Binance USDT-M Futures. Структура кода позволяет добавить другие биржи ccxt (словарь `CCXT_CLASS` и функции, специфичные для Binance).
- Торговля фьючерсами связана с риском потери средств. Перед первым боевым запуском выполните `--dry-run`, а затем проверьте сетку в `demo`.

# Часть 2. place_market_grid.py — сетка условных рыночных ордеров

## 2.1 Назначение и термины Binance

Скрипт выставляет сетку **отложенных рыночных ордеров**: когда цена доходит до уровня, Binance открывает позицию по рынку. Опционально к входам добавляются Take-Profit и Stop-Loss.

Термины Binance, которые используются в скрипте и README:

| Термин | Что это |
|---|---|
| `STOP_MARKET` | Условный рыночный ордер: срабатывает, когда цена **доходит до триггера «по ходу движения»**: BUY при цене ≥ триггера, SELL при цене ≤ триггера |
| `TAKE_PROFIT_MARKET` | Условный рыночный ордер с обратным условием: BUY при цене ≤ триггера, SELL при цене ≥ триггера |
| `triggerPrice` | Цена срабатывания условного ордера (в этом проекте называется «уровень» / «триггер») |
| algo-ордер | С 09.12.2025 все условные ордера Binance идут через отдельный эндпоинт `/fapi/v1/algoOrder`, у них свои идентификаторы `algoId` и `clientAlgoId` |
| `workingType` | Цена, по которой проверяется триггер. Скрипт использует `CONTRACT_PRICE` (последняя цена сделки) |
| hedge-режим | Режим, где одновременно могут быть позиции `LONG` и `SHORT`; каждый ордер несёт `positionSide` |

Это не «стоп-ордера» в обиходном смысле: и вход выше рынка, и вход ниже рынка здесь называются условными ордерами, а их тип (`STOP_MARKET` или `TAKE_PROFIT_MARKET`) определяется автоматически.

## 2.2 Запуск

```
python place_market_grid.py SYMBOL SIDE FILE [EXCHANGE] [MODE] [-p] [-b] [--dry-run]
```

Позиционные аргументы и их порядок такие же, как в Части 1 (`SIDE` обязателен: `long` = BUY, `short` = SELL).

| Ключ | Назначение |
|---|---|
| `-p`, `--profit` | Выставить Take-Profit для каждого ордера (раздел 2.7). По умолчанию выключен |
| `-b`, `--break-even` | Выставить Stop-Loss в безубыток (раздел 2.8). По умолчанию выключен |
| `--dry-run` | Выполнить все проверки, показать план (входы, TP/SL, не ставящиеся TP/SL с причинами), ничего не отправляя |

Ключи `-p` и `-b` независимы: можно указать любой из них, оба или ни одного. Они указываются после `MODE`.

-p / --profit [ДОЛЯ] — выставить Take-Profit (TAKE_PROFIT_MARKET) каждому ордеру.

-p без значения: TP на уровне открытия следующего ордера с учётом спреда; для последнего ордера — по среднему шагу сетки.
-p=0,7 или --profit=0.7: уровень профита считается так же, но TP ставится на 70% пути от входа до него, то есть на 30% ближе к входу, чем уровень следующего ордера с учётом спреда (для последнего ордера то же самое). Разделитель десятичных знаков: . или ,. Допустимые значения: больше 0 и не больше 1. Цена округляется до tickSize, поэтому точная доля не гарантируется.
Указывайте -p после SYMBOL SIDE FILE [EXCHANGE] [MODE]. В PowerShell значение с запятой лучше брать в кавычки: "-p=0,7".

```powershell
python place_market_grid.py ESPORTSUSDT long Bot_levels.csv                       # только входы, demo
python place_market_grid.py ESPORTSUSDT short Bot_levels.csv binance real -p      # входы + Take-Profit
python place_market_grid.py ESPORTSUSDT Long Bot_levels.csv demo -p -b            # входы + TP + SL
python place_market_grid.py ESPORTSUSDT long Bot_levels.csv --dry-run -p -b       # только проверки и план
```

Ключи берутся из того же `.env`, что и в Части 1.

## 2.3 Главное отличие от Части 1: нет batch и нет контроля положения сетки

**Нет batch.** Условные ордера Binance (включая сами входы) выставляются только по одному через `algoOrder`, batch-запросом их отправить нельзя. Поэтому сетка из 50 входов плюс TP/SL — это до ~100 последовательных запросов, обычно несколько секунд. Rate limit при этом не проблема: каждый запрос стоит одну единицу лимита ордеров.

**Нет контроля положения сетки.** Уровни могут быть выше, ниже и вокруг текущей цены. Сохраняется только защитная проверка «не дальше чем в 10 раз от цены» (она ловит опечатки и неверный символ) и проверка «уровень не равен текущей цене» (такой ордер сработал бы сразу).

## 2.4 Тип входа выбирается автоматически

Binance отклоняет условный ордер, который «уже сработал бы» по текущей цене (код `-2021`). Поэтому тип входа зависит от положения уровня относительно текущей цены:

| Сторона | Уровень выше цены | Уровень ниже цены |
|---|---|---|
| `long` (BUY) | `STOP_MARKET` (покупка на пробое вверх) | `TAKE_PROFIT_MARKET` (покупка на падении) |
| `short` (SELL) | `TAKE_PROFIT_MARKET` (продажа на росте) | `STOP_MARKET` (продажа на пробое вниз) |

Если цена находится внутри сетки, часть ордеров получит один тип, часть другой.

## 2.5 Нумерация ордеров: «по направлению прибыли»

Ордера нумеруются по направлению прибыли, независимо от порядка строк в CSV:

- `long`: по **возрастанию** цены (ордер №1 самый низкий);
- `short`: по **убыванию** цены (ордер №1 самый высокий).

«Следующий ордер» (для TP) и номера ордеров для `-b` (4-й и 2-й) считаются в этой нумерации.

## 2.6 Расчёт количества

Как в Части 1: `Size / цена уровня`, округление количества вниз до `stepSize`, цены до `tickSize`. Дополнительно проверяется максимум количества `MARKET_LOT_SIZE`, потому что при срабатывании ордер исполняется как рыночный. Фактическая цена исполнения будет рыночной, поэтому реальная стоимость позиции может отличаться от `Size`.

## 2.7 Take-Profit (`-p`)

Для каждого ордера создаётся `TAKE_PROFIT_MARKET` на **то же количество**, что и у входа, в закрывающую сторону (`long`: SELL, `short`: BUY) с тем же `positionSide`.

**Ордер не последний.** Триггер = уровень **следующего** ордера (по направлению прибыли) с поправкой на спред:

- `long`: уровень следующего **минус** спред;
- `short`: уровень следующего **плюс** спред.

Спред — это `ask − bid` из тикера на момент запуска скрипта. Результат округляется до `tickSize`.

**Последний ордер.** Следующего уровня нет, поэтому используется средний шаг сетки:

```
шаг % = |уровень_N − уровень_1| / уровень_1 / (N − 1)
long : TP = уровень_N × (1 + шаг %)
short: TP = уровень_N × (1 − шаг %)
```

База процента — уровень первого ордера (по направлению прибыли). Делитель `N − 1`, потому что интервалов между N уровнями на один меньше. Например, 8 ордеров на размахе 30% дают шаг 30 / 7 ≈ 4,29%. Если нужна формула «размах / N», это одна строка в функции `build_plan` (место `step = ...`).

Если в сетке один ордер, TP последнего рассчитать нельзя: выводится предупреждение.

## 2.8 Stop-Loss в безубыток (`-b`)

Ставится **один** `STOP_MARKET` для ордера номер `BREAK_EVEN_SL_ORDER` (по умолчанию 4) на количество этого ордера, в закрывающую сторону:

- `long`: триггер = уровень ордера `BREAK_EVEN_LEVEL_ORDER` (по умолчанию 2) **плюс** спред;
- `short`: триггер = уровень этого ордера **минус** спред.

Обе цифры — константы в начале `place_market_grid.py`, их можно менять (должно быть `1 ≤ BREAK_EVEN_LEVEL_ORDER < BREAK_EVEN_SL_ORDER`).

Если в сетке меньше `BREAK_EVEN_SL_ORDER` ордеров, в консоль выводится предупреждение, и сетка выставляется без Stop-Loss.

## 2.9 Какие TP/SL ставятся, а какие нет

Binance не позволяет привязать TP/SL к ещё не сработавшему входу, поэтому TP/SL выставляются заранее как самостоятельные условные ордера. На это накладываются два ограничения, и скрипт ставит только те TP/SL, которые удовлетворяют обоим:

1. **Триггер должен быть с «правильной» стороны от текущей цены.** Иначе Binance отклонит ордер как мгновенно срабатывающий (`-2021`): TP для long (SELL `TAKE_PROFIT_MARKET`) должен быть выше цены, SL для long (SELL `STOP_MARKET`) ниже; для short наоборот.
2. **Цена должна сначала дойти до входа и только потом до TP/SL.** Если триггер TP/SL лежит на пути от текущей цены «раньше» своего входа, он мог бы сработать, когда закрывать ещё нечего (позиции нет), и пропасть. Такие TP/SL тоже не ставятся. Проверку можно отключить константой `STRICT_ENTRY_FIRST = False`, но тогда вся ответственность за такие ордера на вас.

Все пропущенные TP/SL выводятся в консоль до отправки, с причиной (и повторно в конце запуска). Пропуск TP/SL **не считается ошибкой**, входы выставляются в любом случае.

Что это значит на практике (с учётом обоих правил):

| Раскладка сетки | TP (`-p`) | SL (`-b`) |
|---|---|---|
| `long` выше рынка (BUY `STOP_MARKET`) | ставятся все | не ставится (триггер выше цены) |
| `long` ниже рынка (BUY `TAKE_PROFIT_MARKET`) | не ставятся (триггер либо уже за ценой, либо сработал бы раньше входа) | ставится |
| `short` ниже рынка (SELL `STOP_MARKET`) | ставятся все | не ставится |
| `short` выше рынка (SELL `TAKE_PROFIT_MARKET`) | не ставятся (по той же причине) | ставится |
| цена внутри сетки | ставятся для входов «по ходу» от цены | ставится, если вход и триггер подходят |

Другими словами, «каждый следующий ордер открывается при закрытии предыдущего» реализуется заранее только там, где сетка идёт от текущей цены в сторону прибыли. Для остальных случаев потребуется контроль после срабатывания ордеров, он вынесен на следующий этап.

## 2.10 Проверка и повторы

Алгоритм тот же, что в Части 1, адаптированный к algo-ордерам:

1. Все ордера (сначала входы, затем TP/SL) выставляются по одному, у каждого уникальный `clientAlgoId`: `ml…`/`ms…` + время запуска + номер (`E01` вход, `T01` TP, `S04` SL).
2. Запрашиваются открытые условные ордера по символу, и каждый ордер сверяется по `clientAlgoId`: сторона, триггер, количество, `positionSide`.
3. Для отсутствующих запрашивается статус по `clientAlgoId`:
   - биржа не знает такого ордера, он выставляется ещё раз (до 3 раундов), потом снова проверка;
   - ордер уже сработал, отменён или истёк, повторно не ставится (чтобы не задвоить позицию) и попадает в отчёт как проблемный;
   - статус получить не удалось, не ставится повторно, попадает в отчёт.

## 2.13 Проверки перед отправкой

| Проверка | Действие при нарушении |
|---|---|
| Аргументы, структура CSV, символ на `USDT`, символ торгуется в режиме, данные по символу | Ошибка, ничего не отправлено |
| Аккаунт в hedge-режиме | Ошибка (скрипт работает только в hedge) |
| Уровень отличается от цены более чем в 10 раз | Ошибка |
| Уровень равен текущей цене | Ошибка |
| Цена в допустимых пределах, нет дублей после округления до `tickSize` | Ошибка |
| Количество не меньше минимального и не больше максимального для рыночных ордеров; стоимость не ниже min notional | Ошибка |
| Уже стоит условный ордер того же направления на том же уровне (защита от двойного запуска) | Ошибка |
| Маржа для всех входов (`сумма / плечо`) больше доступного баланса | Предупреждение |
| Сумма сетки выше лимита позиции для текущего плеча | Предупреждение |
| `-b`: ордеров меньше `BREAK_EVEN_SL_ORDER`; `-p`: в сетке один ордер | Предупреждение, сетка без этих TP/SL |
| Спред не получен | Предупреждение, TP/SL без поправки на спред |

## 2.14 Ограничения и риски

- **Hedge: позиция общая.** В hedge-режиме все ордера одной стороны по символу работают с одной общей позицией `LONG` (или `SHORT`). TP/SL «привязаны» к входу только по количеству: он закроет такое количество из общей позиции, в том числе из позиции, открытой вручную или другой сеткой по тому же символу.
- Если несколько входов и TP/SL сработают на одном тике, порядок их исполнения биржей не гарантирован. Редкий случай: TP отработает раньше входа и не найдёт позиции.
- Условные ордера не резервируют маржу до срабатывания, поэтому проверка маржи это только предупреждение.
- Скрипт **не отменяет** ордера, не меняет плечо, тип маржи и режим позиций.
- Поддерживается только Binance USDT-M Futures.
- Контроль после срабатывания ордеров (постановка TP/SL после входа и т. п.) не реализован намеренно: скрипт запускается локально, один раз, и завершается.

## 2.15 Коды выхода и частые ошибки

Коды выхода те же, что в Части 1: `0` успех, `1` ошибка проверок (ничего не отправлено), `2` часть ордеров не подтверждена биржей.

| Сообщение | Причина и решение |
|---|---|
| `Аккаунт не в hedge-режиме` | Включите hedge-режим на бирже |
| `уровень равен текущей цене` | Сместите уровень на тик или больше |
| `Binance отклонит (-2021)` в списке не ставящихся TP/SL | Триггер уже за текущей ценой, см. раздел 2.9 |
| `цена дойдет до триггера раньше, чем сработает вход` | См. раздел 2.9, `STRICT_ENTRY_FIRST` |
| `-4005` и подобные в логе размещения | Количество больше максимального для рыночных ордеров, уменьшите `Size` |
| `ПРОБЛЕМА: closed algoStatus=TRIGGERED` в итоговой таблице | Ордер уже сработал за время запуска, повторно не ставится |
| `уже стоит условный ордер` | Сетка уже выставлена, отмените старые ордера, если нужно выставить заново |

# Часть 3. cancel_grid.py — удаление ордеров сетки

## 3.1 Назначение и запуск

Скрипт удаляет ордера сетки, записанные в файл `place_limit_grid.py` или `place_market_grid.py`. Работает с обычными лимитными ордерами (Limit-файлы) и с условными ордерами (Market-файлы).

```
python cancel_grid.py FILE [MODE] [--dry-run]
```

| Аргумент | Обязателен | По умолчанию | Описание |
|---|---|---|---|
| `FILE` | да | — | Файл вида `AIOTUSDT_Short_Limit_04.11-16.49.csv` или `AIOTUSDT_Long_Market_04.11-16.49.csv` |
| `MODE` | нет | `demo` | `real`, `demo` или `testnet` |
| `--dry-run` | нет | выключен | Показать, что будет удалено, и ничего не удалять |

```powershell
python cancel_grid.py AIOTUSDT_Short_Limit_04.11-16.49.csv                  # demo, файл ищется в demo_placed_orders/
python cancel_grid.py placed_orders\AIOTUSDT_Long_Market_04.11-16.49.csv real
python cancel_grid.py AIOTUSDT_Short_Limit_04.11-16.49.csv demo --dry-run
```

- **Символ и тип сетки берутся из имени файла**, поэтому файл нельзя переименовывать. Тип (`Limit` или `Market`) сверяется с колонками внутри файла.
- Если указано только имя файла и его нет в текущей папке, скрипт ищет его в папке выбранного режима рядом со скриптом (`placed_orders/`, `demo_placed_orders/`, `testnet_placed_orders/`).
- Защита от ошибки режима: если файл лежит в папке одного режима (например, `demo_placed_orders/`), а указан другой (`real`), скрипт останавливается с ошибкой и ничего не удаляет.
- Ключи берутся из того же `.env`, что и у остальных скриптов.

## 3.2 Как это работает и как экономятся запросы

1. **Один запрос списка открытых ордеров символа.** Для Limit-файла это обычные открытые ордера, для Market-файла открытые algo-ордера. Тяжёлый запрос `exchangeInfo` не выполняется, ордера адресуются по идентификатору символа.
2. **Решение по каждому ордеру из файла** без дополнительных запросов: ордер, которого нет среди открытых (исполнен или отменён вручную), пропускается.
3. **Удаление только оставшихся ордеров:**
   - **Limit:** batch-отмена `DELETE /fapi/v1/batchOrders`, до 10 ордеров за один запрос (по `clientOrderId`).
   - **Market:** для algo-ордеров batch-отмены по списку Binance не предоставляет. Если нужно отменить **все** открытые algo-ордера символа и других там нет, используется один запрос `algoOpenOrders`. В остальных случаях ордера отменяются по одному.
4. **Проверка по бирже.** После удаления снова запрашиваются открытые ордера. Оставшиеся отменяются по одному (до 2 повторных раундов), затем снова проверка.
5. В конце выводится число запросов к бирже.

Пример: сетка из 25 лимитных ордеров, из них 3 уже исполнены, удаляется 22 ордера за 3 batch-запроса. Всего запросов: синхронизация времени (1), список открытых (1), три batch-отмены (3), проверка (1), то есть 6.

## 3.3 Market-файлы: что удаляется, а что остаётся

Правило: **TP/SL уже сработавшего входа не удаляются**, потому что они защищают открытую позицию.

| Состояние | Что делает скрипт |
|---|---|
| Вход ещё стоит (не сработал) | Удаляет вход и его TP/SL |
| Вход сработал (`TRIGGERING`, `TRIGGERED`, `FINISHED`), его TP/SL ещё стоит | **Оставляет** TP/SL (позиция в работе) |
| Вход отменён или истёк (`CANCELED`, `EXPIRED`, `REJECTED`), его TP/SL ещё стоит | Удаляет TP/SL (он осиротел, закрывать нечего) |
| Статус входа определить не удалось | **Оставляет** TP/SL и выводит предупреждение (безопаснее оставить защитный ордер) |
| Входа нет в файле, а TP/SL стоит | Оставляет и просит проверить вручную |
| Ордера уже нет на бирже (сработал или отменён) | Пропускает, запросов не тратит |

Статус входа запрашивается отдельным запросом **только** для тех входов, которых уже нет среди открытых, но у которых остались открытые TP/SL (один запрос на вход).

Из-за этого правила оптимизация одним запросом `algoOpenOrders` включается только когда удаляется ровно всё, что открыто по символу. Если на символе есть чужие algo-ордера (ручные или от другой сетки) или оставляются TP/SL сработавших входов, ордера отменяются по одному, а чужие ордера не затрагиваются.

## 3.4 Что скрипт не делает

- Не закрывает позиции и не отменяет ордера, которых нет в файле.
- Не удаляет ордера по «старым» файлам других символов: символ берётся только из имени файла.
- В Limit-файле нет TP/SL, поэтому удаляются все стоящие ордера из файла.

## 3.5 Коды выхода и частые ошибки

| Код | Значение |
|---|---|
| `0` | Всё, что нужно было удалить, удалено (или удалять нечего, или `--dry-run`) |
| `1` | Ошибка аргументов, файла, режима или подключения (ничего не удалено) |
| `2` | Часть ордеров удалить не удалось; список указан в итоге |

| Сообщение | Причина и решение |
|---|---|
| `Файл лежит в папке ... а указан режим ...` | Режим не совпадает с папкой файла, укажите правильный режим |
| `Имя файла ... не похоже на SYMBOL_...` | Файл переименован, верните исходное имя |
| `В Limit-файле нет колонки ClientOrderId` | Тип в имени файла не совпадает с содержимым |
| `Биржа отклонила ключи` | Ключи другого режима или нет прав на фьючерсы |
| `Оставлены (позиция в работе или статус неизвестен)` | Это TP/SL сработавших входов: так и задумано |
